# BB Office — Codex 작업 재개 인계

## 0. 새 Codex 세션에 전달할 요청

이 인계 자료와 함께 전달되는 **Claude 컨설팅 결과**를 현재 저장소 코드와 비교해 주세요. 컨설팅 제안마다 확인 근거, 채택/수정/보류 판단을 정리하고, 기존 오피스와 업무 기록을 유지하면서 실제 AI 협업으로 이어지는 최소 실행 흐름부터 구현해 주세요.

사용자의 현재 요청이 우선입니다. Claude 컨설팅은 검토할 제안이며, 자동 업무 실행이나 유료 호출에 대한 승인으로 취급하지 않습니다. 키·계정 연결이 없어도 가능한 코드 진단·설계·구현·모의 검증은 진행하고, 실제 연결이 필요한 부분을 구분해 주세요.

**Claude 컨설팅 결과는 이 파일 작성 시점에 아직 받지 않았습니다.** 사용자가 별도 첨부할 예정입니다. 컨설팅 내용을 임의로 만들어내지 마세요. 첨부가 없으면 현재 코드 진단부터 진행하고, 컨설팅 비교 항목은 미수령으로 남겨 주세요.

## 2. 사용자의 최종 목표

**대표 지시 → 비서실 분담 → 부서별 AI 실행 → 교차 검토 → 실제 결과물 생성 → 대표실 보고·승인**이 이어지는 가상 회사.

- 주요 업무: 품의·문서, 정산·자료 분석, 근태·운영, 기획, 개발 지원.
- 실무는 GPT·Claude 중심. 기존 유료 웹 계정과 개인 프로젝트를 많이 사용함.
- 비서실장은 우선순위·업무 분배·보고 취합을 담당하는 역할.
- 직원들이 실제 파일을 만들고 협업하며, 오피스의 캐릭터·말풍선·대기열에서 실제 진행 상태를 볼 수 있기를 원함.
- 최종 명령과 승인은 대표가 함. 직원에게는 합의된 범위 안의 자율성을 부여함.
- 데일리 회사 업무의 자동 실행은 대상·규칙·일정을 별도로 확정하기 전까지 시작하지 않음.

참고로 사용자가 보여준 영상·설명은 목표 경험의 예시임. 영상 속 기능, Claude Cowork의 특정 스킬, 웹 구독으로 가능한 무인 실행 범위를 확인된 기능으로 단정하지 말 것.

## 3. 반드시 보존할 사용자 선호

- 모니터 3개 중 왼쪽 화면에 오래 켜두는 용도. 공간을 효율적으로 쓰고, 화면 한쪽으로 과도하게 치우치지 않게 할 것.
- 우드 수납장·선반·유리 회의실·라운지가 있는 예전 3D 오피스의 분위기를 좋아함. 현재 분위기를 살리는 변경을 우선함.
- 귀여운 작은 게임 캐릭터. 대표는 슬릭백 머리와 수트. 직원은 서로 구별되는 헤어·복장.
- 기존 무거운 3D 구현에서 팬 소음과 GPU·메모리 부하를 경험함. 가벼운 렌더링과 2D 전환을 유지할 것.
- 이전 실사형 직원과 업로드한 Flame Chubby Buddy GLB 캐릭터는 거절했음. 보관된 실험 자산을 현재 직원으로 다시 적용하지 말 것.
- 고정 운영 주소를 사용함. 사용자에게 수정마다 `?v=office...`가 붙은 새 주소를 주지 말 것. 필요한 캐시 갱신은 내부 모듈/스타일 참조 버전으로 처리함.
- 추가 유지비에 민감함. UI의 직원 수를 늘리는 것과 실제 모델 호출 수·계정·실행 프로세스를 늘리는 것을 구분할 것.

## 4. 현재 실제로 동작하는 기능

### 화면

- 3D 공간과 단순한 절차적 3D 직원. 대표를 제외한 직원은 12명.
- GPT 5명, Claude 4명, Gemini 1명, Copilot 1명, Muse 비서실장 1명.
- 기존 9명은 앉아서 일하거나 라운지에 있음. 추가 지원 직원 3명은 서 있다가 번갈아 통로를 이동함.
- 어깨·팔꿈치 피벗으로 타이핑, 서기, 걷기 팔 자세를 구분함. 서 있는 직원의 팔이 가로로 뻗는 문제는 수정됨.
- 기본 3D는 픽셀 비율 최대 1, 그림자 맵 비활성, 동작 최대 12fps·카메라 최대 24fps, 필요할 때만 렌더링함.
- 일시정지·비활성 탭 정지·모션 감소 설정·WebGL 없는 2D 대체 화면 지원.
- UI 직원 12명이 AI 프로세스 12개를 상시 실행한다는 뜻은 아님.

### 업무와 수동 협업

- 직원·부서별 AI 서비스/개인 프로젝트 바로가기, 브라우저에 업무 배정·보관.
- 공동 업무·회의: 프롬프트를 복사해 각 AI 웹 서비스로 이동하고, 받은 실제 답변을 사용자가 등록함.
- 수동 협업 체인: Claude 계획 → GPT 분석 → Claude 초안 → GPT 검토 → Claude 최종 보고.
- 실제 등록한 답변을 다음 프롬프트에 포함함. 웹 서비스의 답변을 자동 수집하지 않음.
- 협업 최종 결과는 대표 승인 또는 수정 지시를 기다림.

### 마지막으로 완성한 대표 보고 기능

- 상단 ‘보고 등록’, 직원 카드·업무 카드의 ‘대표에게 보고’에서 직원과 실제 결과·확인 내용을 등록함.
- 등록한 직원이 대표실 출입구를 지나 책상 앞에 서고 대표를 바라봄. 말풍선이나 대기열로 내용을 확인함.
- 한 명씩 보고하고, 확인 후 원래 자리로 돌아가면 다음 보고를 처리함.
- 서 있던 지원 직원은 서 있는 자세, 소파 직원은 읽는 자세로 복귀함.
- 소파 직원은 소파 팔걸이와 커피 테이블을 우회함. 이를 위해 라운지 테이블 위치도 조금 조정함.
- 등록된 보고서의 .md 다운로드 지원. 보고 내용을 HTML로 실행하지 않고 텍스트로 표시함.
- 직접 보고의 ‘확인’은 읽음 처리임. 협업 최종 보고의 ‘확인’은 승인을 완료하지 않음.
- 직접 보고는 브라우저 저장 기반임. 사용자가 받은 결과를 등록하는 것이며, AI가 실제로 작업했거나 자동 수집했다고 표시하지 않음.

## 5. 현재 연결되지 않은 기능과 실행기 코드의 범위

현재 운영 화면에는 상주 실행 서버·실제 모델 인증·n8n·Notion·Slack·Discord·중앙 DB·실제 코딩/브라우저 도구가 연결되어 있지 않음. 일상 이동·타이핑은 장식 연출임.

별도로 `runtime/agents.mjs`, `runtime/http.mjs`, `public/autonomy.js`에 API 실행기와 UI 코드가 있으나 기본 화면은 이를 로드하거나 호출하지 않음.

- GPT·Claude 텍스트 API를 통한 분담 → 순차 작업 → 교차 검토 → 최종 보고 → 승인·수정 처리.
- 한 번에 진행 업무 1개, 업무당 최대 12회 호출, 응답당 최대 1,800토큰, 수정 최대 2회.
- 서버 JSON 기록 저장. 재시작 중이던 업무는 실패로 표시하고 자동 재실행하지 않음.
- 브라우저 조작, 파일 편집, 코드 실행, 검색 도구는 없음. 결과 문서의 내용 생성과 실제 도구 실행을 구분해야 함.
- 현재 실행기 허용 직원은 기존 GPT·Claude ID 6개임. UI의 12명과 실행기 목록을 통합할 필요가 있음.
- 테스트는 모의 공급자로 검증했으며 실제 API 연결·과금·24시간 운영을 검증한 상태는 아님.
- API 키·모델명·인증 토큰은 서버 환경변수로 설정하는 구조. 키나 토큰을 인계 문서·채팅·저장소에 넣지 말 것.
- 승인 API는 결과 확정 기록임. 외부 발송·결제·제출·배포·삭제 기능은 없음.

Muse 비서실장은 역할 명칭임. muse.ai 영상 서비스에 범용 비서 오케스트레이션 기능이 있다고 가정하지 말 것. `employees.js`의 `model` 필드는 과거 외형 모델 구분 용도가 섞여 있으며 실제 LLM 모델 설정과 동일하지 않음.

## 6. 코드 진입점

기본 실행 경로:

`public/index.html → office-loader.js → office-hybrid.js → game-crew.js / office-furnishings.js / office-reports.js`

- `public/app.js`: 업무 보드·직원/부서 카드·프로젝트·배정·대시보드.
- `public/employees.js`: 직원·역할·고정 ID·위치·프로젝트 연결.
- `public/web-workflow-core.js`, `web-workflow.js`: 수동 협업·수정·대표 승인.
- `public/meeting.js`: AI별 웹 작업·답변 등록·회의록 다운로드.
- `public/staff-report-core.js`: 직접 보고 데이터 검증과 작성자 매핑.
- `public/staff-report-compose.js`: 보고 입력·브라우저 저장·보고 이벤트.
- `public/office-reports.js`: 협업/직접 보고 대기열·읽음·다운로드·이동 중개.
- `public/report-routes.js`: 대표실 좌표·보고 이동 경로.
- `public/ambient-routes.js`: 지원 직원의 일상 이동. 업무 실행 상태로 취급하지 않음.
- `public/game-crew.js`, `crew-arm-pose.js`: 캐릭터와 팔 자세.
- `runtime/agents.mjs`, `runtime/http.mjs`, `server.mjs`: 미연결 API 실행기 및 로컬 서버.
- `test/`: 범위·승인·저장 복원·직원·자세·동선·보고 데이터 검증.

`public/office.js`와 과거 모델/농구/GLB 실험 파일은 기본 화면의 진입점이 아님. 파일이 존재한다는 이유로 활성 기능으로 해석하지 말 것.

브라우저 저장 키:

- `jbco-plays`: 업무
- `jbco-web-workflow`: 수동 협업
- `jbco-meeting`: 회의
- `jbco-staff-reports`: 개별 보고
- `jbco-report-acks`: 보고 읽음

기존 키·직원 ID·프로젝트 링크를 보존할 것. 브라우저 저장을 중앙 공유 DB로 간주하지 말 것. 실제 업무 데이터와 환경변수 값은 이 인계 자료에 포함하지 않았음.

## 7. 재현과 검증

Node.js 20 이상. package.json에 외부 npm 런타임 의존성은 없으며 Three.js는 public/vendor/에서 제공함.

```bash
npm run check
npm test
npm start
```

기본 로컬 주소는 http://localhost:3000/ . 포트 변경은 `PORT=3019 npm start`처럼 설정함. 서버 시작 시 비공개 실행 기록 폴더 `.office-data/`가 만들어질 수 있으며 gitignore 대상임. `.env`, `.office-data/`를 게시하지 말 것.

확인된 결과:

- 기능 기준 커밋에서 문법 검사 통과, 단위 테스트 36개 통과.
- 브라우저에서 직접 보고의 작성자·대표실 이동·말풍선·대기열 순서·일시정지·마크다운 다운로드·읽음 복원 확인.
- 지원 직원과 소파 직원의 보고·원래 자세 복귀 확인.
- 협업 최종 보고는 확인 후에도 승인 대기를 유지함.
- 2D/모션 감소 환경에서 보고 등록·확인 가능.
- 고정 운영 주소에서 새 보고 기능과 복귀까지 확인. 검증 중 GLB나 API 요청은 없었음.

이전 세션의 Playwright 브라우저 검증 스크립트·스크린샷은 개발 환경 임시 파일에 있음. 새 세션에서 사용할 수 있다고 가정하지 말 것. 저장소의 npm test는 브라우저 자동화 테스트를 포함하지 않음. 새 환경의 사용 가능한 브라우저 도구로 재현할 것.

최소 브라우저 재현:

1. 상단 ‘보고 등록’에서 ‘자료정리 지원’ 직원을 선택하고 테스트 문서를 입력함.
2. 그 직원이 대표실로 이동하고 말풍선을 띄우는지 확인함.
3. 보고를 하나 더 등록해 중복 이동 없이 순서대로 처리하는지 확인함.
4. 보고 내용을 열고 .md를 내려받은 뒤 ‘확인 · 자리로’를 누름.
5. 첫 직원이 서 있는 위치로 돌아가고 다음 직원이 보고하는지 확인함.
6. 소파 직원을 선택한 보고도 재현하고, 확인 후 읽는 자세로 복귀하는지 확인함.
7. 새로고침 후 읽은 직접 보고가 재등장하지 않는지 확인함.
8. 별도로 협업 최종 결과를 등록해 보고 읽음과 대표 승인이 분리되는지 확인함.

실제 회사 자료 없이 테스트용 입력으로 검증할 것. 키·연결이 없으면 모의 실행기를 사용하고 실제 API/도구 검증 범위를 명시할 것.

## 8. Claude 컨설팅 결과를 반영하는 절차

1. 최신 코드·현재 변경·위 인계 자료와 Claude 답변을 확인함.
2. Claude 제안을 현재 구현과 대조함. ‘이미 있음 / 수정 필요 / 새로 필요 / 근거 확인 필요’를 구분함.
3. 다음 표를 제안별로 채움: `제안 | 현재 코드 근거 | 채택·수정·보류 | 이유 | 변경 파일 | 검증 방법`.
4. 사용자 목표·비용·기존 기록·성능·승인 원칙에 맞는 최소 증분안을 선택함.
5. 우선 한 업무의 접수 → 분담 → 실제 도구/파일 결과 → 검토 → 대표 보고·승인 흐름을 완결함. 업무 후보는 품의 초안 준비이며, 실제 회사 업무를 임의로 실행하지 않음.
6. 코드와 모의 검증을 진행하고, 실제 연결에 필요한 계정·실행 환경·비용 범위를 구체적으로 정리함.
7. 이번 변경의 적절한 검사와 브라우저 재현을 완료하고, 실제 확인한 범위와 남은 연결을 보고함.

우선 검토할 설계 간극:

- UI 직원 12명과 실행기 직원 6개의 역할 레지스트리 통합.
- 계정/공급자·실행 에이전트·역할·업무·하위 작업·파일·보고·승인의 데이터 모델.
- 공통 지침·자료 버전과 진행 중 업무의 재계획.
- 실제 실행 이벤트를 현재 대기열·직원 상태에 연결하는 인터페이스.
- 상주 실행 환경, 복구, 비용 한도, 관측 가능성.
- 기존 유료 웹 계정/공식 도구로 가능한 범위와 별도 API가 필요한 범위.

Claude 제안에 n8n·Notion 등이 포함되어도, 현재 프로젝트에서 필요한 역할과 연결 시점을 검토해서 선택할 것.

## 9. 변경·배포 시 유의사항

- 기존 파일·기록과 사용자의 변경을 먼저 확인하고 작업 범위를 좁힐 것. 처음부터 다른 앱으로 교체하지 말 것.
- 소스 main과 정적 게시 gh-pages는 별개임. 소스만 바뀌었다고 사이트에 반영되었다고 말하지 말 것.
- 문서만 변경하면 Pages를 다시 배포할 필요가 없음.
- 화면 변경을 게시할 때는 public/을 정적 배포 대상으로 삼고, 브랜치 이력을 보존함. 강제 푸시를 기본 절차로 삼지 말 것.
- 바뀐 모듈과 부모 import 참조의 내부 버전을 함께 갱신해 이전 브라우저 캐시가 섞이지 않도록 함.
- 사용자에게 줄 운영 링크는 항상 https://joonhobrianbaek.github.io/jbco/ .
- 배포 완료 상태와 실제 공개 화면을 확인하고 결과를 보고함.
- 데일리 업무 자동 실행, 외부 발송, 유료 API 실행 등은 현재 사용자 요청과 확정된 운영 범위를 확인한 후 연결함.
