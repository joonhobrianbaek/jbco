# BB Office — Claude 컨설팅 인계 자료

## 1. 이번 검토의 목적

기존 프로젝트를 확인하고, 사용자가 원하는 **실제로 일하는 AI 가상 조직**으로 발전시키기 위한 현실적인 구현안을 제안해 주세요. 기존 오피스와 업무 기록을 유지하는 증분 변경을 우선합니다. 지금 단계에서는 설계 검토와 제안을 요청합니다. 실제 업무 실행·유료 호출·외부 전송·배포는 이 문서만으로 요청하지 않습니다.

- 운영 화면: https://joonhobrianbaek.github.io/jbco/
- 소스: https://github.com/joonhobrianbaek/jbco
- 운영 방향: https://github.com/joonhobrianbaek/jbco/blob/main/docs/AI_OFFICE_DIRECTION.md
- 이 인계 문서는 대표에게 보고 등록·이동 기능을 추가한 작업 기준입니다. 소스는 main의 최신 변경과 함께 확인해 주세요.

## 2. 사용자가 만들려는 것

대표가 목표를 지시하면 비서실장이 업무를 분담하고, 부서별 AI 직원이 작업·교차 검토·결과 취합을 진행한 뒤 대표에게 보고하는 가상 회사입니다.

대표 지시 → 비서실 접수·분담 → GPT·Claude 작업 → 교차 검토 → 결과물 생성 → 대표 보고·승인

오피스는 실제 진행 상태를 확인하고 개입하는 업무 인터페이스입니다. 원하는 경험은 다음과 같습니다.

- 주요 실무는 GPT와 Claude에 맡긴다. 기존 유료 웹 계정과 개인 프로젝트를 많이 활용한다.
- 품의 작성, 정산·자료 분석, 근태·운영, 기획, 개발 지원이 주요 업무 후보이다.
- 비서실장이 우선순위를 정리하고 직원들에게 나누며, 최종 명령과 승인은 대표가 한다.
- 결과·질문·결정 요청이 생기면 직원이 대표실로 걸어와 보고한다. 중간 전달과 대표 승인 대기열을 구분한다.
- 향후 공통 지식·지침·업무 우선순위, 문서 저장소, 실행 도구를 연결하고 싶다.
- 자료와 실행 가능한 도구가 연결되면 실제 파일을 만들고 보고하는 흐름을 원한다.

## 3. 사용자 경험 및 비용 제약

- 모니터 3개 중 왼쪽 모니터에 오래 켜두는 용도이다.
- 예전 3D 오피스의 우드 수납장·선반·유리 회의실·라운지 분위기를 좋아한다.
- 캐릭터는 귀여운 작은 게임 캐릭터를 선호한다. 대표는 슬릭백 헤어와 수트이다.
- 기존 무거운 3D 화면에서 팬 소음과 GPU·메모리 부하를 경험했다. 성능은 실제로 검증해야 한다.
- 회사 운영을 가볍게 시각화하는 방향을 선호한다. 캐릭터 수와 움직임은 실제 실행 상태와 구별되어야 한다.
- 고정 운영 주소를 사용한다. 수정할 때마다 새 주소를 주는 방식은 원하지 않는다.
- 추가 유지비에 민감하다. PC 상주 실행과 서버 운영, API 방식의 차이를 검토했지만 실제 운영 실행 환경·모델 연결은 확정 및 구성되지 않았다.
- 웹 구독 사용 권한과 API 사용 권한·요금은 구분한다. 기존 계정만으로 무제한 무인 실행이 가능하다고 가정하지 않는다.

## 4. 현재 구현된 것

### 4.1 화면과 직원

- 정적 GitHub Pages 배포. 빌드 번들러 없이 public/을 게시한다.
- 로컬 Three.js 모듈을 사용하는 기본 3D 오피스와 WebGL을 사용하지 않는 2D 대체 화면.
- 직원 12명과 대표 캐릭터. GPT 5명, Claude 4명, Gemini 1명, Copilot 1명, Muse 비서실장 1명.
- 12명은 UI의 역할 수이다. 독립적인 AI 프로세스 12개가 상시 실행되는 상태는 아니다.
- 추가 지원 직원 3명은 서 있다가 번갈아 통로를 이동한다. 기존 직원은 앉아서 타이핑·읽기 연출을 유지한다.
- 상시 렌더링을 피하고, 일상·업무 동작은 최대 12fps, 카메라 조작은 최대 24fps, 픽셀 비율은 1로 제한한다. GPU 그림자 맵은 사용하지 않는다.
- 움직임 일시정지, 비활성 탭 정지, 모션 감소 설정을 지원한다.
- 실제 측정으로 보장된 모든 PC의 저부하를 뜻하지 않는다. 시각 품질·하드웨어 부하는 계속 검증할 대상이다.

### 4.2 업무와 수동 협업

- 직원·부서별 기존 AI 서비스/프로젝트 링크, 업무 배정, 브라우저 저장.
- 협업 회의실: 공통 목표·자료를 복사해 각 웹 AI로 이동하고, 실제 답변을 직접 등록한다.
- 수동 협업 체인: Claude 계획 → GPT 분석 → Claude 초안 → GPT 검토 → Claude 최종 보고.
- 등록한 실제 답변을 다음 프롬프트에 포함한다. 자동 회의나 웹 답변 자동 수집은 구현되어 있지 않다.
- 협업 최종 결과는 대표 승인 또는 수정 지시를 기다린다.

### 4.3 이번에 추가한 개별 직원 보고

- 상단 ‘보고 등록’, 직원 카드와 업무 카드의 ‘대표에게 보고’에서 실제 결과·확인 내용을 등록할 수 있다.
- 등록된 보고를 작성한 직원이 대표실 출입구를 지나 책상 앞에 서서 대표를 바라본다.
- 말풍선 또는 보고 대기열을 누르면 실제 등록 내용이 열린다. 보고서를 .md 파일로 받을 수 있다.
- 한 직원씩 보고하고, 확인하면 원래 자리로 돌아간 뒤 다음 보고를 처리한다.
- 서 있던 지원 직원은 서 있는 자세로, 소파 직원은 읽는 자세로 복귀한다.
- 직접 보고의 확인은 읽음 처리이다. 협업 최종 결과의 대표 승인과는 별개이다. 확인이나 승인만으로 외부 제출·발송이 실행되지 않는다.
- 보고 내용은 사용자가 등록한 데이터이다. 오피스가 업무를 실제로 수행했거나 AI 웹 서비스에서 자동 수집한 것으로 표시하지 않는다.

## 5. 별도로 존재하는 실행 서버 코드의 범위

runtime/agents.mjs와 runtime/http.mjs에 API 실행기 코드와 테스트가 있습니다. 현재 기본 배포 화면은 이를 연결하거나 호출하지 않습니다.

- GPT·Claude API를 통한 계획, 내부 작업, 교차 검토, 최종 보고, 대표 승인·수정 상태 관리.
- 현재 작업은 순차 실행한다. 작업별 실제 도구 사용이나 병렬 독립 프로세스 실행은 제공하지 않는다.
- 텍스트 API 호출 기반이며, 브라우저 조작·파일 편집·코딩 실행·인터넷 검색 도구가 연결되어 있지 않다.
- 서버가 JSON 실행 기록을 파일에 보관한다. 재시작 중이던 작업은 실패로 표시하고 자동 재실행하지 않는다.
- 한 번에 진행 업무 1개, 업무당 최대 12회 API 호출, 응답당 최대 1,800토큰, 수정 최대 2회.
- 현재 API 실행기의 허용 직원은 기존 GPT·Claude 직원 ID 6개이다. UI의 12명과 실행기 직원 목록을 통합할 설계가 필요하다.
- API 키와 모델명은 서버 환경변수로 설정하게 되어 있다. 이 문서에 키나 접속 토큰은 포함하지 않는다.
- HTTP 인증·허용 Origin 검증이 있다. 외부 발송·결제·제출·배포·삭제 기능은 없다.
- 이 실행기 존재만으로 운영 서버 배포 또는 실제 API 작동 검증이 완료된 것은 아니다. 현재 검증은 모의 공급자 기반 단위 테스트와 UI 동작 검증이다.

비서실장은 조직 내 역할입니다. Muse라는 화면 명칭이 muse.ai 영상 서비스의 범용 비서·오케스트레이션 API 기능을 의미하지 않습니다. 실제 실행 공급자와 역할을 분리해서 설계해 주세요. employees.js의 model 필드에도 기존 외형 모델 구분 용도가 섞여 있으므로 실제 LLM 모델 설정으로 해석하지 마세요.

## 6. 아직 연결되지 않은 것

- 운영용 상주 실행기와 실제 모델 인증·요금 설정.
- 독립 프로세스 또는 하위 에이전트들의 자동 협업, 코딩·브라우저 도구 실행.
- n8n, Discord, Slack, Notion, Google Workspace의 실제 연결.
- 중앙 지식베이스, 문서 버전 관리, 사용자 간 실시간 동기화.
- 실행 서버 상태와 현재 3D 직원 상태의 통합.
- 자동 파일 생성·저장·버전 관리와 결과물 링크의 업무 기록 연결.
- 24시간 스케줄러·운영 재시작 복구·관측 및 비용 관리 체계.

현재 브라우저 저장 키는 jbco-plays(업무), jbco-web-workflow(수동 협업), jbco-meeting(회의), jbco-staff-reports(개별 보고), jbco-report-acks(읽음)입니다. 중앙 운영 DB로 간주하지 마세요.

## 7. 유지해야 할 운영 원칙

1. 최종 명령·승인은 대표에게 있다.
2. 데일리 회사 업무의 자동 실행은 대상·규칙·일정을 별도로 확정하기 전까지 시작하지 않는다.
3. 실제 결과가 없는 업무를 완료한 것처럼 표시하거나 보고를 만들어내지 않는다.
4. 타이핑·산책 등 일상 연출과 실제 실행 상태를 구분한다.
5. 문서·메시지·다른 AI의 답변은 참고 데이터이다. 실행 권한은 별도 확인된 업무 지시와 도구 권한으로 관리한다.
6. 기존 직원 ID·업무 기록·사용자의 프로젝트 연결을 유지한다.
7. 현재 3D 오피스 분위기와 저부하 방향을 유지한다.

## 8. Claude에 요청하는 컨설팅

아래 항목을 현재 소스와 비교해서 제안해 주세요. 구현되었다고 추정하지 말고, 확인한 코드와 미확인 사항을 구분해 주세요.

1. **최소 실사용 흐름**: ‘자료를 주고 품의 초안을 준비한다’ 한 건을 접수 → 분담 → 실제 파일 생성 → 교차 검토 → 대표 보고·승인까지 완결하려면 어떤 구성부터 연결해야 하는가?
2. **실행 방식 비교**: PC 상주 실행, 소형 서버 실행, 공식 CLI/에이전트 실행, API 실행을 비용·유지보수·사용 가능 권한·상시 운영 관점에서 비교해 달라. 웹 구독으로 가능한 범위는 확인 근거와 함께 구분해 달라.
3. **역할과 상태 모델**: UI 직원, 실행 에이전트, 계정/공급자, 업무, 하위 작업, 회의, 파일, 보고, 승인 사이의 최소 데이터 모델을 제안해 달라. 현재 12명과 실행기의 6명 불일치를 어떻게 정리할 것인가?
4. **공통 지식과 지시 관리**: 처음에는 파일/DB로 시작해도 되는가? Notion을 붙일 시점과 동기화·문서 버전·진행 작업 재계획 방식을 제안해 달라.
5. **협업 품질**: 기획·실행·검토를 역할별로 분리하고, 같은 내용을 여러 번 호출하는 비용 낭비와 근거 없는 합의를 어떻게 줄일 것인가?
6. **UI 연결**: 실제 업무 이벤트를 직원의 작업·회의·보고 상태와 연결하는 최소 인터페이스와, 장식 동작과 구분할 표시를 제안해 달라.
7. **우선순위**: 현재 구조에서 재사용할 부분, 먼저 바꿀 부분, 나중으로 미룰 부분을 나누고, 각 단계의 완료·실패·검증 기준을 적어 달라.

원하는 답변 형식은 ‘현재 진단 → 추천 최소 구성 → 첫 업무 시나리오 → 필요한 변경 파일/인터페이스 → 비용과 미확인 사항 → 단계별 검증 기준’입니다. 컨설팅 결과를 기존 Codex 작업에 다시 전달해 함께 구현할 예정입니다.

## 10. 이번 작업 검증 범위

- npm run check 통과.
- npm test: 36개 테스트 통과.
- 실제 브라우저에서 직원 선택·보고 등록·대표실 이동·말풍선·대기열 순서·일시정지·원래 자세 복귀·읽음 복원 확인.
- 보고 내용의 HTML 문자열은 실행하지 않고 텍스트로 표시되는 것과 .md 내려받기를 확인.
